# 内部功能演示手册

> 创建时间：2026-11-23 05:26

给同事演示这套系统能干什么。25–30 分钟，七幕，照着点即可。

**这不是业务验收。** 演示的是系统账面能力，不是仓库现场作业能力。两者的差别在第二节写清楚了，被问到别混。

## 一、演示能到哪一步

一场演示能走完「来货 → 上架 → 下单 → 分配 → 拣货 → 复核 → 发运 → 退货」的完整链路，中间每笔数量变化都能在库存台账和流水里对上。有三处必须在演示时绕开，见第五节。

```mermaid
flowchart LR
    A[双入口] --> B[来货上架]
    B --> C[货主下单]
    C --> D[分配拣货]
    D --> E[复核发运]
    E --> F[波次分播]
    F --> G[库内作业]
    G --> H[作业端]
```

七幕合计约 25 分钟，留 5 分钟给提问。如果时间紧，砍掉第六、七幕（波次分播、作业端），留下前五幕——主线不受影响。

## 二、能演与不能演

| 能力 | 演示 | 说明 |
|---|---|---|
| 主数据与库位建模 | 能演 | 按仓型校验库位坐标，配错会被拒 |
| 来货、收货、上架、留样 | 能演 | 破损与好货分账，留样自动拆行 |
| 出库下单、FEFO 分配、拣货、复核、发运 | 能演 | 复核超差拦截是亮点 |
| 波次生成、播种墙分播 | 能演 | 异步生成，界面不卡 |
| 补货、盘点、移库 | 能演 | 补货需先压低拣选位库存才能触发，见第三幕 |
| 退货入库、报废与转回 | 能演 | |
| 货主门户 | 能演 | 建单、查进度、查库存，与后台实时同步 |
| 对外接口 | 能演示接口文档，不演示真实对接 | `docs/api/openapi-owner.json` |
| 面单与标签打印 | **不能演** | 打印代理未接入，页面是说明页 |
| 移动作业执行 | **不能演** | 手机上只能领任务和扫码定位，执行页是 PC 布局 |
| 计费与账单 | **不能演** | 未实现 |
| 上游 ERP 同步 | **不能演** | 未实现 |
| 性能与容量 | **不能演** | 只压过 200 单波次，别报日单量数字 |

## 三、开演前的准备

### 环境

后端和前端任选一种起法，演示前 10 分钟确认好。

```bash
# 方式一：本机跑（改代码后最快）
docker compose -f docker-compose.dev.yml up -d
cd backend && .venv/Scripts/python -m uvicorn src.main:app --port 8000
cd frontend && npm run dev

# 方式二：容器全栈（最接近交付形态）
docker compose up -d --build
```

本机跑时后台在 `http://127.0.0.1:5173`，门户在 `http://127.0.0.1:5174`，作业端在 `http://127.0.0.1:5173/m/tasks`。容器跑时三者都在 `http://localhost:8080` 下，分别是 `/admin/`、`/owner/`、`/m/tasks`。

注意门户在 dev 模式下需要单独构建：`npm run build:owner` 后 `npx vite preview --mode owner`，端口 4174，地址是 `http://127.0.0.1:4174/owner/`。

### 账号

| 用途 | 账号 | 密码 |
|---|---|---|
| 后台 | `admin` | `Admin@12345` |
| 货主门户 | `OWN002` | `Owner@123456` |

后台登录页有滑块验证，鼠标拖到底即可。

### 演示数据

库里现成可用的：

- 货主：`OWN001 华南食品`、`OWN002 测试货主`
- 商品：`SKU000001 饼干`（启批次）、`SKU000002 苏打水`（启批次）、`SKU000003/4 共享编码`（不启批次）
- 库位：`RCV-01` 收货区、`F2-A-01` / `F2-B-01~10` 存储区、`PK-01` 拣选区、`SMP-01` 留样区，共 21 个
- 库存：饼干可用 19 件（存储 2 + 存储 5 + 拣选 12），苏打水可用 72 件

**演示前必做两件事**，否则会看到一堆无关单据：

1. **清掉波次压测残留**。库里有 60 张 `BULK-` 前缀的拣货中订单，会塞满拣货页。

```sql
-- 仅删压测数据，不碰走查单
DELETE pl FROM wms_outbound_pick_line pl JOIN wms_outbound_pick p ON p.id = pl.pick_id
  JOIN wms_outbound_order o ON o.id = p.order_id WHERE o.owner_doc_no LIKE 'BULK-%';
DELETE p FROM wms_outbound_pick p JOIN wms_outbound_order o ON o.id = p.order_id
  WHERE o.owner_doc_no LIKE 'BULK-%';
DELETE a FROM wms_outbound_allocation a JOIN wms_outbound_order o ON o.id = a.order_id
  WHERE o.owner_doc_no LIKE 'BULK-%';
DELETE l FROM wms_outbound_order_line l JOIN wms_outbound_order o ON o.id = l.order_id
  WHERE o.owner_doc_no LIKE 'BULK-%';
DELETE FROM wms_outbound_order WHERE owner_doc_no LIKE 'BULK-%';
DELETE FROM wms_outbound_wave WHERE code IN ('WAV000006','WAV000007','WAV000008');
DELETE FROM wms_outbound_wave_rule WHERE code LIKE 'P4ACC%' OR code LIKE 'P4R%';
```

2. **把拣选位库存压到补货线以下**，第五幕才能触发补货建议。`PK-01` 的补货下限是 10、上限 20，当前 12 件，正好不触发。

```bash
curl -X POST http://127.0.0.1:8000/api/v1/wms-inventory/adjustments \
  -H "Authorization: Bearer <admin token>" -H "Content-Type: application/json" \
  -d '{"request_id":9001,"sku_id":1,"lot_id":0,"location_id":24,"stock_status":"available","delta":-8}'
```

`location_id=24` 就是 `PK-01`。调完拣选位剩 4 件，低于下限 10。

演示用库位的 id：`F2-A-01` = 1、`RCV-01` = 21、`SMP-01` = 22、`PK-01` = 24。

## 四、七幕脚本

### 第一幕：两条独立入口（2 分钟）

**操作**

1. 后台登录页展示，不要登，先讲
2. 切到门户登录页
3. 门户用 `OWN002` 登录，进概览页
4. 讲一句「门户只有概览、子账号、入库预报、出库订单四个菜单」

**讲什么**

后台和门户是两套产物、两个登录接口、两套路由。货主账号从后台登录会被拒，员工 token 打开门户会被清会话送回本端登录页。这不是隐藏菜单，是登录环节就分开。

**看点**：门户侧边栏只有四项，后台侧边栏有主数据、库存、入库、出库、库内作业、逆向、任务。

### 第二幕：来货到上架（6 分钟）

**操作**

1. `入库 → 入库预报`，新建一张预报。货主选 `华南食品`，商品选 `SKU000001 饼干`，应收 200，会展开批次子表
2. 填两个批次：`20261015` 应收 150，`20261102` 应收 50。提交
3. `入库 → 收货`，按刚建的预报开收货单。实收按批次填：`20261015` 收 150、破损 3；`20261102` 收 50
4. 确认收货，去 `库存 → 库存查询`，展开商品行，看到 `RCV-01` 上有 146 件可用、3 件破损
5. `入库 → 上架`，找到刚生成的上架任务，目标库位分别填 `F2-A-01`，逐行确认
6. 回 `库存 → 库存查询`，看 `F2-A-01` 上两批的数量与批次
7. `库内作业 → 留样台账`，有一件从 `20261015` 批次拆出来的留样，在 `SMP-01`

**讲什么**

- 破损单独记，不进可发池，也不会和好货混在一起
- 留样是按比例自动拆的，不是人工挑，留样区在分配时被排除
- 上架时库位是必填的，填错温区的库位会被提示

**预期数字**

| 位置 | 批次 | 数量 |
|---|---|---|
| RCV-01 | 20261015 | 可用 146 + 破损 3 |
| RCV-01 | 20261102 | 可用 50 |
| F2-A-01 上架后 | 20261015 | 146 |
| F2-A-01 上架后 | 20261102 | 50 |
| SMP-01 | 20261015 | 留样 1 |

如果走查数据和演示数据叠加，数字会有出入，以页面上「本次收货单对应的批次」为准，别死背总数。

### 第三幕：货主下单到分配（5 分钟）

**操作**

1. 切到门户 `出库订单`，表单里填：货主单号 `DEMO-001`，类型 C 端，收件人、地址随便填，商品选 `DUP01`，数量 2，提交
2. 看列表最上面出现新单，状态「待分配」
3. 切到后台 `出库 → 出库订单`，按货主单号搜 `DEMO-001`
4. 点分配。分配后订单状态变「已分配」
5. 切回门户刷新列表，状态变「已分配」

**讲什么**

- `owner_id` 由会话注入，货主传别家 id 也查不到
- 分配只锁定量、不动库存，发运时才真正扣减
- 分配按先到期先出挑批次，同批号不会跨效期

**看点**：跨端状态同步是这一幕最直观的东西，两个窗口并排放着刷。

### 第四幕：拣货、复核、发运（6 分钟）

**操作**

1. `出库 → 拣货`，找到刚分配的单，生成拣货单
2. 拣货单里按行确认，扫码或手工填库位
3. `出库 → 复核与发运`，找到这张单，**先填一个明显偏小的实称重量**，提交，被拒
4. 提示超差后，改成合理值再提交
5. 点发运。运单号留空或随便填
6. `库存 → 库存流水`，按商品筛，看这三笔：入库、分配不产生流水、发运扣减

**讲什么**

- 复核称重和理论重量比对，超差必须重检，这是防错发
- 库存只有库存域能写，任何变动都在同一事务里落流水
- 流水只追加不修改，过账按来源单据幂等——同一张单点两次只算一次

**这一幕会露怯的地方**：发运后没有面单，运单号是空的。见第五节。

### 第五幕：库内作业（4 分钟）

**操作**

1. `库内作业 → 补货建议`，点「扫描并生成建议」
2. 列表里会出现 `PK-01 上的饼干`，建议补整数（按箱规取整）
3. 点执行。再看库存：存储位减、拣选位加，总量不变
4. `库内作业 → 盘点单`，随便建一张，填实盘数量，提交后看差异
5. `库内作业 → 移库单`，把几件从一个存储位挪到另一个

**讲什么**

- 补货按整箱取整，不拆箱——拆零会让拣选位出现散箱
- 补货执行时重新校验来源库存，不够就整笔拒绝，不部分补
- 重复执行同一建议不会重复补货

**前置条件**：`PK-01` 当前库存必须低于 10，否则不出建议。见第三节的准备步骤。

### 第六幕：波次与分播（5 分钟，可选）

**操作**

1. 先用门户或后台建 10–20 张出库订单，货主都用华南食品，商品选有库存的那个
2. `出库 → 波次看板`，新建一条规则：不填截单时间、不填承运商，单波上限填 20
3. 生成波次。进度条原地推进，页面不卡
4. `出库 → 分播作业`，选刚生成的波次，生成格口
5. 扫商品或填商品 ID，页面告诉你应放哪个格口
6. 故意填错格口，被拒

**讲什么**

- 生成是异步的，`POST /waves` 落一条记录立刻返回，后台任务逐单分配
- 每 50 单让出一次事件循环，探活期间登录接口一直可用
- 播种墙一个格口绑一单，扫错格口直接拒绝

**不要演**：中途中止。中止与生成存在竞态，取消后可能残留 1–3 单仍是拣货中，见第五节。

### 第七幕：作业端（2 分钟，可选）

**操作**

1. 切到缩成 390 宽的窗口，打开 `/m/tasks`
2. 登录（共用后台账号）
3. 领一个任务
4. 切到 `扫码` 页，输入任务号回车，页面定位到该任务

**讲什么**

- APK 与浏览器共用同一份前端产物，不做条件编译
- 扫码广播优先，拿不到广播就走键盘模拟，两种形态同一条路径
- 浏览器低于 Chrome 110 会被挡住并给明确提示，不是白屏

## 五、四处会露怯的地方

提前打招呼，比被现场问出来好。

| 地方 | 会发生什么 | 怎么说 |
|---|---|---|
| `出库 → 打印模板` | 是一张说明页，写着「接入前需要两件东西」 | 「打印还在设计器阶段，今天不演。」直接跳过，别点 |
| 发运那一步 | 没有面单，运单号空着 | 「面单走本地打印代理，还没接。」 |
| 移动端点进任务执行 | 跳到 PC 版拣货页，表格挤在 390 宽里 | 只演领任务和扫码定位，别点「去拣货」 |
| 波次看板的「中止」 | 取消后可能残留 1–3 单仍是拣货中 | 不演中止 |

## 六、预判提问

**问：三万单一天跑得动吗？**
「没压过。只压过 200 单一个波次，生成 14 秒，期间接口正常响应。真实量级的连接数、索引、长事务都还没验证。」

**问：货主能看到我们的成本吗？**
「看不到。门户只有四项菜单，接口层面 `owner_id` 由会话注入，前端连参数都传不了。」

**问：两个人同时改同一个库位的库存会怎样？**
「库存行加锁，后到的事务等锁后基于最新数量算。P1 验过两事务并发各扣 50，库存 70，结果一个成功一个被拒，最终 20。」

**问：重复提交同一张单会不会重复入库？**
「不会。过账按来源单据幂等，唯一键冲突直接返回已处理。收货单重复确认则被状态机挡住，返回 422。」

**问：这套东西能直接上生产吗？**
「账面能力齐了，现场能力差两块：移动端作业页、打印。计费也还没做。」

## 七、演砸了怎么办

演示前备份一次数据库：

```bash
docker exec huoling-mysql mysqldump -uhuoling -phuoling123 --single-transaction --no-tablespaces \
  --set-gtid-purged=OFF huoling_wms --result-file=/tmp/demo_backup.sql
```

单子建错了、数量填错了不用回滚，演示就是把错拦下来的过程。真把库存搞乱了，再从备份还原。

演示中途改代码必重启后端，单进程 uvicorn 不重启不生效。重启后别演波次——启动会把超时的生成中波次标为中断。
