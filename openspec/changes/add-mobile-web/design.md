# Design

## Context

`openspec/specs/wms/mobile-app/` 现有的六条需求默认作业端就是 APK。但 `/m/*` 本来就是同一 SPA 里的一组路由，浏览器打开它天然可用——只是没人把这个形态写进规格，于是版本门槛的表述也跟着变成"只对 Android 生效"。

## Decisions

### W1 一份构建，两种装载

```
frontend/dist  ──┬──> nginx 静态目录        → 浏览器访问 /m/*
                 └──> Capacitor 打包 APK    → PDA 安装
```

前端不做条件编译，不区分形态。运行时只判断一件事：能否拿到扫码广播。拿得到就用广播，拿不到就走键盘模拟输入框——这条降级路径在蓝图里已有，只是当时它被描述成"PDA 的兜底"，现在它是"两种形态的共同路径"。

**为什么不给浏览器形态单独做一个精简版界面。** 精简意味着两套布局、两套交互、两处修 bug。三万单场景下作业员的耐心比包体大小值钱。

### W2 版本门槛按形态分流

| 形态 | 卡什么 | 卡在哪 |
|---|---|---|
| APK | Android 系统版本 14+ | 安装阶段，`minSdk` 直接拒绝 |
| 浏览器 | 浏览器主版本 | 打开页面时读 UA，低于范围就挡在门口 |

浏览器下限取 Chrome 110、Safari 16.4。取这个值是因为 Element Plus 2.14 与 Vue 3.5 的目标环境在那里；再往下要加 polyfill，收益不抵成本。

**不支持 IE、不支持任何 Chromium 90 以下的国产浏览器内核。** 这类浏览器的用户会看到明确的版本提示，而不是一个点不动的页面。

### W3 打印与扫码不受形态影响

浏览器形态同样走打印代理——代理是局域网 HTTP 服务，浏览器直接 `POST` 给它即可，不需要 APK 的桥接能力。这也是为什么打印不能退回浏览器原生打印：三万张面单走不通，跟形态无关。

## Risks / Trade-offs

- **浏览器形态被当成"完整替代"** → 扫码枪走键盘模拟时，如果焦点不在输入框上，扫出来的字符会丢。P5 的验收要覆盖"焦点丢失后重新聚焦"这条。
- **两种形态的会话时长不一致** → 浏览器标签页常驻不关，token 过期后表现为"点了没反应"。处理方式是接口返回 401 时统一跳登录，不做静默重试。
- **UA 判断浏览器版本不可靠** → 部分国产浏览器会伪装 UA。兜底是功能探测（检测用到的 API 是否存在），UA 只用于给出提示文案。
