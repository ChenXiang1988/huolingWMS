# Design

## Context

现有系统里没有"工单"，只有两类东西：业务单据（ASN、order、receipt 等，各自有集中状态机）和作业任务 `wms_tasking.task`（只存调度指针，不存业务明细，P5 定的 I5 原则是任务不重写业务状态机）。真实仓库要多一层"单据 → 工序 → 任务"，规格见 `spec.md`。设计要处理的核心矛盾是 `domain-map` 的硬约束：一个能力只归一个域，若同时改变两个域的状态必须拆开。

## Goals / Non-Goals

**Goals:**

- 给出工单的域归属，使其不违反"一能力归唯一域"。
- 定义工序链如何驱动既有状态机而不重写它。
- 明确工序生成的任务如何接入现有 `wms_tasking.task`，并处理设计与实现的字段偏差。

**Non-Goals:**

- 不实现派工、指派到人或拆分到 PDA，那是 `task-dispatch-split`。
- 不引入到货签到工序的具体实现，那是 `arrival-check-in-doc`。
- 不改 8 份常驻规格与任何业务域的状态机。

## Decisions

### 工单归任务域，但定位为编排层而非调度指针

`domain-map` 定义任务域是"作业执行的载体"。工单若直接改入库、出库、库内作业域的状态，就违反"同时改变两个域状态要拆开"。解法是把工单定位为任务域内的**编排层**：它只持有工序链、进度指针和完成事件，不持有业务状态字段。业务动作一律通过 `register_handler` 回调既有域接口完成，工单在回调成功后再关闭自己的工序。

这样工单改变的是"任务域自己的编排状态"，不是"业务域的业务状态"，域归属成立。代价是工单进度与业务状态存在短暂不一致窗口，由下一条决策处理。

替代方案是把工单塞进主数据域当"单据目录"，被排除——主数据是被引用的静态事实，工单是执行中的动态编排，职责不符。

### 工序完成走既有状态机的 transit 边，不另建状态机

D9 要求每个单据在本域 `states.py` 声明状态集合与迁移边，所有状态变更走同一个 `transit(doc, event)`，禁止接口直接赋值。工序完成事件只投递一个 `event` 给业务域，由业务域自己的迁移边决定是否合法；工单不复制一份业务状态。

但当前实现里 `states.py` 与 `transit` 尚未落地，各 service 仍直接赋值 `status=`（inbound、tasking 均如此）。因此本变更的实施前置是补齐 D9 的状态机基础设施，否则跳序拦截无处落脚。这一点列为 tasks 的首组任务。

### 工序实例与工序定义分离

工序定义（工序类型、前后置、完成条件）是配置，按单据类型存一份；工序实例是每张工单运行时生成的具体工序，带执行状态与结果。之所以分两张表：定义是"作业标准"，实例是"这次做到哪一步"，两者生命周期不同；混在一张表里会让每次建工单都复制配置，改配置时无法回溯历史工单走的是哪版工序链。

### 任务接入复用 ref_type / ref_id，统一命名偏差

设计文档写的是 `target_type / target_id`（data-model.md L260），实现用的是 `ref_type / ref_id`（wms_tasking/models.py L26-27）；单号前缀设计 `TK`，实现 `TSK`；`task_type` 设计枚举含 receipt / sample_dispose，实现只有 transfer / count / putaway / pick / check。工序生成的任务要接入，必须先选定一侧为准。本变更以**实现为准**（ref_type/ref_id、TSK），因为已落库的数据改列名成本高，而设计文档可直接修订。同时把工序类型作为新的 `ref_type` 值 `work_order_step` 注册，走既有 `register_handler` 契约。

### 工单幂等键独立于货主单号

现有幂等键 `(owner_id, owner_doc_no)` 只覆盖货主建单。仓库自建工单没有货主单号，新增幂等键 `(owner_id, source_type, source_id, step_type)`：同一来源单据的同一工序只生成一条工序实例。工单 code 走新前缀 `WO`。

## Risks / Trade-offs

- **进度与业务状态不一致窗口**：工序回调成功到工单记录完成之间若进程崩溃，会出现业务已推进但工序显示未完成。→ 幂等键保证重放只补记进度，不重复执行业务动作；实施时把回调与进度写入放同一事务，跨域用事件补偿。
- **D9 基础设施缺失**：跳序拦截依赖 `transit`，当前未实现。→ 首组任务先补状态机，补不齐则本变更不能进入验收。
- **命名偏差未决**：设计文档与实现的字段、前缀不一致，本变更选了实现侧。→ 实施时同步修订 data-model.md 的相关条目，避免文档继续分叉。
- **子工单拆分规则会随货量变化**：按商品还是按数量拆，取决于真实工单结构。→ 本次只定义两种拆分方式与汇总约束，具体触发阈值留待 `scale-capacity-review` 用实测数据定。
