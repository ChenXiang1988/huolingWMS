# Design

## Context

现有 `wms_tasking` 的实现只有抢单一条路：`claim_task` 用 `with_for_update` 锁行、`status != pending` 拒绝、`recycle_timeout` 超时回归且注释明确"不做自动改派"。工序链变更（`work-order-process-chain`）会把工序转成任务，本变更要在其上加派单与拆分。规格见 `spec.md`。

## Goals / Non-Goals

**Goals:**

- 定义派单与抢单如何共存，以及并发下如何保证单一归属。
- 定义父子任务的数据结构与汇总规则。
- 明确超时处理从"一律回归"扩展为"按分配方式分流"的落点。

**Non-Goals:**

- 不实现工序链本身，依赖 `work-order-process-chain` 的工序实例。
- 不实现 PDA 界面，只定义按指派人过滤的契约。
- 不引入消息队列或分布式锁，单进程内用数据库行锁解决并发。

## Decisions

### 指派人与领取人分两个字段

`claimed_by` 已是领取结果，语义是"谁实际抢到或提交了"。系统派单是"系统指定谁来做"，与领取结果不同——派单后作业员仍需点领取才开始。因此新增 `assignee_id` 存指派目标，`claimed_by` 保留原语义。两者可以不同（改派场景下尤其明显），规格里要求可区分。

替代方案是复用 `claimed_by` 直接写入指派人，被排除：那样领取动作无法与派单区分，超时判断拿不到真实的领取时间。

### 父子关系用 parent_task_id 自关联，不建独立拆单表

子任务与父任务的字段完全同构（同样的 task_type、ref_type、目标位置、分配方式），只是多一个拆分序号和数量。建独立表会重复一套字段与状态机。自关联代价是汇总时要递归查询，但拆分只有一层（父 → 子），没有多层嵌套，递归深度固定为 1，可接受。

### 派单规则按优先级匹配，无命中落公共池

规则可组合（作业区、在手量、技能、工位），按优先级依次匹配，先命中生效。这与此前波次规则、选位优先级的既有写法一致。无规则命中时转公共池而不是报错或随机派——保证工序不被分配问题卡住。

### 超时处理按 dispatch_mode 分流

`recycle_timeout` 当前对全部 `claimed` 任务一律回归。改为按 `dispatch_mode` 分支：抢单任务维持回归（不自动改派，守住 P5 的既有行为）；派单任务按配置的超时策略改派或转池。这样既有抢单行为零变化，只有新类型任务走新逻辑。

### 并发控制统一走行锁

派单、领取、改派都走 `SELECT ... FOR UPDATE` 锁任务行，状态校验后写入。与现有 `claim_task` 一致，不引入新机制。单进程假设见 tech-stack。

## Risks / Trade-offs

- **单进程假设**：行锁方案在多 worker 下仍依赖数据库行锁本身，但 P0 明确不支持多 worker。→ 规模问题留给 `scale-capacity-review`，本变更不预设分布式方案。
- **父子任务状态机复杂度**：子任务失败时父任务如何回退尚无既成规则。→ 本变更只定义"未完成子任务不计入汇总、父任务保持进行中"，具体重派或重试由业务决定，不写进规格。
- **派单字段与工单字段重叠**：`step_id` 与工序实例的关联和工单的工序字段可能重复。→ 只存工序实例标识，不复制工序定义，避免两处维护。
- **超时策略配置缺失**：改派或转池的选择需要配置入口。→ 作为子任务字段 `timeout_action`，默认值取转池，避免无配置时任务卡死。
