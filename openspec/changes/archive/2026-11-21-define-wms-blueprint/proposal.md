# Proposal

## Why

货灵 WMS 目前只有一句定位——"单仓执行、管理四面墙内的操作"——加上"用 ApeAdmin 做管理基座"这个技术决定。领域怎么切、插件怎么挂、库存归谁管、先做哪一段，全部空白。

直接开工的代价是可预期的：入出库各造一张库存表、任务模型在三个插件里各写一遍、跨插件直接读写对方的表把事务边界打散。单仓规模下这些错误不会立刻报错，要等对不上账才暴露。

先定蓝图，是因为 ApeAdmin 已经把"边界"做成了物理形态——一个业务域一个包，启用禁用联动菜单——边界划错的返工成本远高于多花一轮谈清边界。

## What Changes

- **十个业务域定边界**。主干五域按物料流转阶段切分：入库 → 库存 → 库内作业 → 出库 → 逆向，首尾相接不重叠；支撑五域按性质切分：主数据、任务执行、计费、报表、集成。
- **一域一插件**。每个域落成 `backend/src/plugins/builtin/<domain>/` 下的独立包，`plugin.json` 的 `dependencies` 声明强依赖，依赖方向单向不回头。
- **多货主是第一维度**。商品档案、库存、单据全部按货主归属；货主方用户只能看到自己的数据；跨货主共用库位时，正确性由作业环节的三者一致校验保证，而不是靠物理隔离。
- **库存台账唯一真相**。只有 `wms_inventory` 能写库存数量；任何增减与流水在同一事务内完成；流水只追加不修改；过账按来源单据幂等。库位内的状态转换（可用、冻结、破损）同样走记账契约，只记一条带前后状态的流水。
- **批次与效期按商品开关**。启用的商品收发货必带批次，出库默认先到期先出，临期自动冻结；未启用的商品归入默认批次，界面不出现批次。
- **出库同时支持大货与电商**。订单带类型，走同一套流程的两条分支：B 端整箱整托、边拣边分；C 端拆零、波次加播种。日单量三万级，波次生成异步执行。
- **拆零靠补货支撑**。存储区的整箱货补到拣选区才能拆零，补货按库位上下限触发，是 C 端拣货的前提。
- **复核用称重拦截**。打包后与订单理论重量比对，超差拦下重检——三万单量级下，错发的代价远高于称一次。
- **打印走本地代理**。面单与标签用热敏打印机，指令经局域网代理下发；浏览器直接打印只保留给 A4 文档类。
- **只验货，不质检**。到货核对是收货环节的一部分，记录应收、实收、破损与差异原因，不建质检单据、不做检验判定。
- **留样是一种存储位置**。货主按每次来货提服务订单，要求留样才留；数量可写固定件数或按来货比例向上取整；留样上架到专用库位，分配不从中取货，仓储费与常规库存分开计算；到期可报废、延期、邮寄到指定地址或转回可发。
- **库位坐标随仓型解释，选位规则不随仓型变**。一套坐标字段承载平面仓、楼层仓、立库三种定位方式；上架顺序固定为「专属库位 → 同商品就近 → 按仓型」，暂存区与留样区永不进入候选。仓型是仓库配置项，不是多仓支持。
- **计费从作业事实派生**。费用不是人工录入的结果，而是由已完成的单据与每日占用快照换算；费率变更不追溯；账单月结后锁定，调整走红冲。
- **货主有两个入口，共用一套规则**。系统对接走 API，人工操作走自助端；两个入口都调同一份建单服务，货主身份由凭证或登录态决定，不接受请求体指定。API 规范由本系统单方面定义并版本化，货主系统负责接入。
- **货主账号分两级**。一个货主一个主账号，主账号可建子账号并指定操作员或只读；子账号不能建号、不能跨货主。货主侧只用三个固定角色，不支持自定义。
- **作业端出 APK，货主端只在桌面**。Android 14 及以上，一套 Web 构建通过容器打进一个作业端安装包；货主自助端按桌面浏览器设计，不出安装包也不做窄屏适配。两端都不做离线。
- **分期路线 P0–P8**。每期是一个能独立验收的 change，本期只产蓝图，不写业务代码。
- **显式不做**：多仓切换、序列号级追踪、质检判定、跨货主合单、货主端移动端、iOS 客户端、对接财务系统、插件 ZIP 热装前端页面、AGV 与自动化分拣线调度。

## Capabilities

### New Capabilities

- `wms/domain-map`: 十个业务域的职责边界、插件拓扑、跨域调用规则、单仓多货主前提、对外接口归属与分期归属，约束后续每一次 WMS 变更把功能放进正确的域
- `wms/stock-ledger`: 库存数量以台账为唯一真相的记账约束——唯一写入者、同事务流水、只追加、幂等过账、按货主粒度记账与隔离
- `wms/billing`: 费用从已完成作业与每日占用派生、费率不追溯、费用只追加、账单月结锁定的计费约束
- `wms/owner-access`: 货主的两个入口如何进来、能做什么、身份如何确定，以及两个入口共用同一套业务规则
- `wms/mobile-app`: 移动作业端的交付形态——一套前端怎么变成 APK、客户端不获得额外信任、版本门槛、不做离线，以及货主端明确不出安装包
- `wms/location-policy`: 库位坐标编码、空间域判定、上架选位优先级，以及仓型作为配置项而非多仓的边界
- `wms/lot-control`: 批次开关、批次建立、先到期先出、临期自动冻结、批次不可合并
- `wms/wave-picking`: 出库双模式、波次规则与生成、分播两法、补货触发、称重拦截、面单打印

### Modified Capabilities

无。仓库当前没有任何既有 spec。

## Impact

- 后续所有 WMS 变更的边界判定与 `plugin.json` 依赖声明，都以本蓝图为准。
- 本期不触碰代码。仓库当前只有 `openspec/` 与 `CODEBUDDY.md`，`backend/`、`frontend/` 尚未存在。
- 分期顺序决定目录骨架、插件包的落地次序，以及哪些能力在拿到 PDA 之前只能由 PC 操作台代执行。
- 三条约束会直接影响后续实现，需要提前知道：多货主意味着商品、库存、单据、列表查询全部带 `owner_id` 维度，货主归属只以商品档案为唯一来源；启用批次后库存粒度是 `(owner, sku, lot, location, status)`，幂等键必须含批次，否则同一商品的多批次过账会被判为重复；插件无法携带前端页面，因此业务插件随仓库发布而非 ZIP 热装。
- 计费域新增一张每日占用快照表，是唯一需要按日冻结数据的域。它的存在让 P8 之前必须保证库存历史可回溯。
- 货主 API 引入第二套凭证体系，与后台 JWT 并行。两套凭证不能互相越界，这是本期定下的接口约束。
- 货主自助端不新建工程，是同一前端里的独立路由组与独立菜单树。这意味着前端要加一层「按身份切换菜单根」的逻辑，属于 P0 的布局改造范围。
- 移动端引入 Android 构建链（容器工程、签名、内部分发），是本期唯一新增的工程门类。它不产生新的业务域，但会产生一个必须维护的发版流程。
- 日单量三万级这个事实，把波次与补货从"可选优化"变成"主链路"。出库域因此成为工作量最大的一块，P4 单独立期。
- 打印方案从浏览器打印改为本地代理加热敏打印机，是唯一被推翻的技术选择。仓库要备至少两台面单打印机与一台标签机。
- 技术栈已定稿。基座把绝大部分铺好了，全部新增依赖是后端三个（`apscheduler`、`qrcode`、`openpyxl`）加前端一个（`dayjs`）。运行形态：全栈 Docker Compose、APScheduler 进程内定时任务、pytest 窄范围测试、不部署 Redis、浏览器打印加二维码标签、不做前端国际化、不引 ESLint、不建 CI。完整清单见 `design/tech-stack.md`。
