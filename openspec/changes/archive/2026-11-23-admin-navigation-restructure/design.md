# Design

## Context

见 proposal.md 的 Why。当前菜单由基座 seed 与插件 seed 写入数据库,前端按登录用户拿到的菜单动态注册路由并渲染侧栏。已初始化的库不会因为 seed 改动自动删除或移动菜单;启动时基座 seed 先于插件 seed 执行,插件各自维护自己的目录与页面。

## Goals / Non-Goals

**Goals:**

- 导航分组按员工实际动作划分,不按单据来源划分。
- 已有库启动时原位迁移菜单父级,保留页面记录、按钮权限与角色绑定。
- 门户根留在菜单表,后台侧栏不展示;两个入口继续共用一套菜单数据。

**Non-Goals:**

- 不改单据字段、建单接口与权限模型。
- 不迁移服务订单、退货单,它们是仓库侧建单。
- 不改货主门户自身的页面结构。

## Decisions

**客户服务目录建在基座 seed,不建在业务插件。** 该目录跨入库与出库两个域。各业务插件卸载时按权限前缀或 path 前缀清理菜单,放在任一插件里会被单域停用连带删除,导致另一域的子页变成孤儿。备选方案是放进 `wms_inbound`,因上述联动删除风险否决。

**作业台继续建在出库插件。** 三个页面全属出库域,权限前缀一致,单域停用时应一起清理。这与客户服务的选择相反,依据是目录是否跨域。

**迁移采用改 `parent_id`,不重建 Menu 记录。** 按钮权限以页面 id 为父级,角色绑定也指向菜单 id;重建记录会丢掉这些关联。实现顺序是先在新父级下找,找不到再到旧父级找并改挂,都没有才新建。

**门户隔离放在前端侧栏过滤,不在后端菜单接口过滤。** 后台与货主门户共用同一套菜单接口,后端按端过滤会让门户失去自己的菜单。前端按顶级 path 过滤只影响后台侧栏。

**404 页按浏览器路径判断所在端。** 同一个组件被两个 router 复用,router 内部路径不含 base,无法区分前后台;浏览器路径带 `/owner/` 或 `/admin/`,可以直接判断。

## Risks / Trade-offs

- [旧书签失效] 页面完整路径变化 → 接受,不保留旧路径重定向;404 页可回到首页。
- [管理员手动改过菜单] 若页面已被移到自定义目录,迁移逻辑找不到旧父级,会在新目录下再建一条 → 升级后检查菜单管理页,影响范围限于手工调整过的环境。
- [客户服务目录被手动删除] 基座增量 seed 下次启动补建,插件 seed 再迁移页面 → 可自愈,不需要人工恢复。

## Migration Plan

```mermaid
flowchart LR
    A[部署后端] --> B[基座 seed 补建客户服务]
    B --> C[插件 seed 迁移订单与作业页面]
    C --> D[验证侧栏与按钮权限]
    D --> E[部署前端]
```

回滚时前端恢复旧分组文字,但页面路由已变;后端菜单父级需手工改回。优先在菜单管理页调整,不做数据库整体回滚。
