# Design

## Context

门户页面现状：商品档案（`sku/index.vue:71-111`）表单与列表同屏且表单常驻；出库订单（`order/index.vue:136-238`）列表在上表单在下，另有一个手写详情抽屉（241-289）；入库预报（`asn/index.vue:76-107`）只有表单没有列表，提交后清空表单并显示成功提示，用户无处查单。

后台范式是列表 + 页内 `el-drawer`：`wms_master_data/owner/index.vue:31-38,163-193` 与 `wms_inbound/asn/index.vue:41-50,164-220` 都是点击新建弹抽屉、提交后关抽屉刷新列表。但全项目 20 处抽屉均各页手写，没有共享骨架。用户此前定过 PC 端右侧抽屉标准：头部标题/副标题/状态标签/关闭，主体左侧分段目录 + 右侧两列字段，底部操作右对齐。

后端入库预报只有 `POST /wms-inbound/portal/asns`（`api.py:709`），没有列表/详情接口。`WmsAsn` 模型有 `source`、`status`、`expect_arrive_at` 等字段可展示。

## Goals / Non-Goals

**Goals:**

- 把门户三个混排页面改成"列表为主、抽屉录入"，让用户在任一时刻只面对一种任务。
- 建一个两端共用的抽屉骨架组件，后续新页面直接复用。
- 补齐预报列表与详情，让提交结果可追踪。

**Non-Goals:**

- 不新增独立新建页路由；仍用页内抽屉，路由表不变。
- 不一次性替换后台已有的 20 处抽屉；本次只让新组件可用，后台既有页面保持原样（见 Decisions 第 3 条）。
- 不改创建单据/商品的业务规则与服务端校验。
- 不做窄屏适配（设计文档 D18：门户按 1280 以上宽度设计）。

## Decisions

### 1. 共享抽屉组件用"插槽 + 数据"混合 API

新建 `frontend/src/components/AppFormDrawer.vue`：

- props：`modelValue`（开关）、`title`、`subtitle`、`status`（可选标签文本）、`sections`（分段目录数据，用于生成左侧导航）、`width`（默认 720px）。
- slots：`header-extra`（头部附加）、每个分段一个命名插槽 `section-<key>`（内容为两列字段表单）、`footer`（底部操作，默认右对齐）。
- events：`update:modelValue`、`close`。

选择混合 API 而非纯 props：字段表单的控件类型各异（输入、下拉、日期、明细行表格），纯数据驱动会退化成 schema 渲染器，复杂度远超复用外壳的收益。插槽让页面只提供内容，组件只管骨架与行为。

### 2. 分段目录只在 sections ≥ 2 时显示

用户定过的标准里有"左侧分段目录（段数≥3 才显示）"。本次实现按更实用的阈值：sections 长度为 0 或 1 时隐藏左侧目录，主体直接铺满；≥2 时显示目录并支持点击定位。商品建档分"基本信息"和"批次与效期"两段，会显示目录；出库订单建单只有一段，不显示。

### 3. 后台既有抽屉不强制迁移

共享组件先服务本次三个门户页面。后台 20 处手写抽屉保持不变，避免一次改 20 个文件、引入回归风险。组件本身两端可用，后续页面或重构时逐步替换。spec 里"两端共用组件"约束的是**新实现的抽屉**，不是要求立即重写历史代码。

### 4. 页面拆分方式：列表页保留，表单移入抽屉

- `sku/index.vue`：删常驻表单，保留列表与「新建商品」按钮；点按钮开抽屉，提交成功后 `drawerVisible=false; await load()`。
- `order/index.vue`：删常驻建单表单，保留列表与筛选、工具栏加「新建订单」；详情抽屉改用 `AppFormDrawer`。
- `asn/index.vue`：页面主体改为"我的预报"列表 + 「新建预报」按钮；原表单移入抽屉；列表数据来自新增的 portal 接口。

三页共同的交互契约：提交成功 → 关抽屉 + 刷新列表 + 明确提示；提交失败 → 抽屉保持打开 + 显示错误 + 表单内容不变。

### 5. 预报列表/详情接口放 `wms_inbound` 插件

新增 `GET /wms-inbound/portal/asns` 与 `GET /wms-inbound/portal/asns/{id}`：

- 列表返回本货主的预报（单号、货主单号、状态、预计到货、提交时间），按提交时间倒序，分页。
- 详情返回明细行，`owner_id` 不匹配时返回 404（与出库订单 portal 详情一致，不泄露是否存在）。
- 查询条件强注入会话 `owner_id`，不接收请求体里的 owner_id。

### 6. 不新增路由、不改菜单

三个页面仍是 `/owner/sku`、`/owner/order`、`/owner/asn` 三个路由，只改页面内部结构与抽屉。菜单、权限、seed 全部不动，避免与 `separate-portal-menu-management` change 冲突。

## Risks / Trade-offs

- [共享组件 API 需要页面配合改造] 三个页面都要重写模板 → 接受；这是本次核心工作。
- [后台抽屉未统一] 用户标准说"两端所有抽屉统一"，但本次只有门户三页用新组件 → 已在 Non-Goals 与 Decision 3 说明，后续 change 可逐步迁移后台。
- [预报列表可能数据量大] 三万单量级 → 接口分页，默认 20 条，与出库订单列表一致。
- [抽屉里放明细行表格] 入库预报有多行明细 → 抽屉宽度默认 720px，明细表在抽屉内横向滚动；不新增复杂的全屏编辑模式。

## Migration Plan

1. 前端：加 `AppFormDrawer.vue`，依次改 sku/order/asn 三页，跑 typecheck 与 build:owner。
2. 后端：加预报列表/详情接口，重启触发 reload。
3. 验证：用 own001 登录，逐页确认默认无表单、点新建弹抽屉、提交后关抽屉并刷新、详情抽屉外观一致。
4. 回滚：前端回退组件与三页改动；后端撤回两个新接口。
